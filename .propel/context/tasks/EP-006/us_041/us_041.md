# User Story - US_041

## Story ID
* ID: US_041

## Story Title
* Async OCR Processing and Status Tracking

## Description
* As a clinician, I want uploaded documents processed via OCR asynchronously with status tracking so that extracted content is available for clinical review within 2 minutes without blocking the upload interface.

## Acceptance Criteria
1. **Given** a clean document is successfully uploaded, **When** the file is persisted, **Then** an OCR processing job is queued and the document record is updated with status "Queued."
2. **Given** an OCR job is queued, **When** the background worker processes it using Tesseract, **Then** the document status transitions through "Processing" → "Completed" and the extracted text is stored against the document record.
3. **Given** OCR processing completes, **When** I check the document status, **Then** the status shows "Completed" and the extracted text is available within 2 minutes p95 for files up to 10 MB.
4. **Given** an OCR job fails, **When** the failure is detected, **Then** the document status is updated to "Failed," the error is logged, and the job is retried up to 3 times with exponential backoff before moving to the dead-letter queue.

## Edge Cases
* What happens if the document is a scanned image with very low text quality? (OCR produces a low-confidence extraction; the document is flagged for manual review with the raw OCR output stored.)
* How does the system handle concurrent OCR jobs? (Queue workers process jobs in parallel up to a configured concurrency limit; back-pressure is applied when the queue depth exceeds the threshold.)
